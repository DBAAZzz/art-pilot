# 资产管理 v1 方案

## 背景

Art Pilot 当前已经有“最近任务”区域，用于展示图片生成任务的过程状态：

```txt
生成中 -> 找到图片 -> 完成 / 失败 / 取消
```

最近任务可以让用户看到刚刚发生了什么，但它不应该承担长期资产管理职责。资产管理应该面向“已经生成出来、可以长期保存、查找、整理和复用的图片结果”。

因此，资产管理 v1 的核心目标是：

```txt
最近任务 = 生成过程记录
资产管理 = 长期图片资产库
```

## 模块边界

### 最近任务

最近任务以 `jobId` 为核心对象。

它回答的问题是：

- 这个生成任务现在是什么状态？
- 这次任务生成了几张图？
- 是否还在运行？
- 是否失败或取消？
- 这次任务用了什么 prompt 和参考图？
- 我能不能取消这个任务？

适合展示：

- prompt 摘要
- 任务状态
- 生成时间 / 完成时间
- 生成数量
- 参考图
- 任务内图片缩略图
- 取消任务
- 打开图片所在位置

不适合承担：

- 长期图库浏览
- 图片级搜索
- 收藏
- 标签
- 批量操作
- 导出
- 删除和整理
- 资产复用工作流

### 资产管理

资产管理以 `imageId` 或具体图片文件为核心对象。

它回答的问题是：

- 我现在拥有哪些可用图片资产？
- 如何快速找到某张图？
- 这张图当时怎么生成的？
- 这张图能不能继续复用？
- 如何整理、收藏、导出或删除这些资产？

适合展示：

- 图片网格
- 图片详情
- prompt 快照
- 图片参数
- 文件信息
- 所属任务
- 参考图关系
- 收藏 / 标签 / 筛选
- 批量操作
- 复用入口

## 核心决策

资产管理首页不展示“任务卡片”，而展示“图片资产卡片”。

原因：

- 用户进入资产管理时，通常想找一张图，而不是找一次任务。
- 一个任务可能生成多张图，最终被复用和管理的是单张图片。
- 图片资产可以独立收藏、删除、导出和继续创作。
- 任务信息应该作为图片详情的一部分，而不是主列表的组织方式。

```txt
RecentTaskList:
  task -> images

AssetManagement:
  image -> task context
```

## 信息架构

### 页面结构

资产管理 v1 建议采用三段式结构：

```txt
筛选区 / 分类区
  -> 图片资产网格
  -> 图片详情面板
```

如果初版开发要更轻，可以先做两栏：

```txt
图片资产网格
  -> 图片详情面板
```

筛选区可以后续补上。

### 图片资产网格

每个卡片对应一张图片。

卡片建议展示：

- 图片缩略图
- 收藏状态
- 生成时间
- 比例
- 尺寸
- 状态
- 是否有关联参考图

卡片默认不展示完整 prompt，避免网格变得拥挤。prompt 可以用 tooltip、搜索命中摘要或详情面板展示。

卡片操作：

- 单击：选中并打开详情
- 双击：预览大图
- 右键或更多菜单：
  - 在 Finder 中显示
  - 复制图片
  - 复制 prompt
  - 基于此图继续创作
  - 删除

### 图片详情面板

详情面板围绕单张图片展示完整上下文。

建议字段：

- 图片预览
- 创建时间
- 状态
- 宽高
- 比例
- 文件大小
- 文件名
- prompt 快照
- 生成参数摘要
- 参考图列表
- 所属任务 `jobId`
- 同任务其他图片
- Codex thread id
- 清理状态

其中高级信息可以默认折叠：

- generation params
- `jobId`
- `codexThreadId`
- 原始 Codex 路径摘要
- cleanup status
- cleanup error

### 高级参数

AI 图片资产的复用不能只依赖 prompt 和比例。真正影响结果可复现性的参数应该作为一个整体保留下来。

详情页建议增加“高级参数”折叠面板，用于展示生成时的完整参数快照。

建议展示：

- model / checkpoint
- size
- aspectRatio
- seed
- steps
- sampler
- CFG Scale
- image count
- provider
- provider version
- 参考图数量

当前 Codex 生图链路未必能拿到所有参数，但数据结构应提前预留。拿不到的字段可以为空，不要在 UI 中伪造。

### 筛选和排序

v1 优先支持：

- 全部图片
- 最近生成
- 收藏
- 有参考图
- 失败 / 异常资产
- 按月份

排序优先级：

- 生成时间倒序
- 生成时间正序
- 文件大小
- 图片尺寸

搜索优先支持：

- prompt 文本
- 文件名
- jobId

后续可以支持：

- 标签
- 自定义相册
- 按比例筛选
- 按尺寸筛选
- 按来源筛选

## 资产操作

### 基础操作

v1 应支持：

- 预览图片
- 在 Finder 中显示
- 复制图片
- 复制 prompt
- 收藏 / 取消收藏
- 删除图片

删除需要谨慎处理：

- 删除图片文件前应二次确认。
- 删除数据库记录和删除文件要有清晰策略。
- 如果只从资产管理中移除但保留文件，需要在 UI 中明确表达。

### 复用操作

资产管理的关键价值是让图片能再次进入创作流程。

建议支持：

- 使用同样 prompt 再生成
- 基于此图作为参考图继续生成
- 使用同任务参数再生成
- 打开所属任务上下文

点击“基于此图继续创作”时，可以跳转到创作页并预填：

- prompt
- aspectRatio
- imageCount
- generation params
- reference image

### 批量操作

v1 可以先预留，不一定立刻实现。

后续支持：

- 多选
- 批量导出
- 批量删除
- 批量收藏
- 批量打标签
- 批量移动到相册

## 数据模型建议

当前图片历史已经围绕 `generation_tasks` 和 `generated_images` 建立。

资产管理需要把 `generated_images` 提升为主查询对象。

建议图片资产至少包含：

```txt
imageId
jobId
imagePath
imageUrl
index
width
height
fileSize
createdAt
prompt snapshot
generationParams
aspectRatio
status
favorite
tags
cleanupStatus
cleanupError
```

其中：

- `prompt snapshot` 可以来自所属任务，但长期建议在图片资产查询结果中直接返回。
- `generationParams` 应保存为 JSON，用于还原影响生成结果的核心参数。
- `favorite` 和 `tags` 可以后续迁移加入。
- `imageUrl` 继续通过 custom protocol 生成，不直接暴露本地文件路径给 renderer 展示。

### Generation Parameters

建议新增 `generation_params` JSON 字段，挂在任务或图片资产上。

如果参数对同一任务内所有图片一致，可以先保存在 `generation_tasks`。如果未来同一任务内不同图片拥有不同 seed 或后处理参数，则应支持图片级覆盖。

推荐结构：

```json
{
  "provider": "codex",
  "model": "gpt-image-1",
  "checkpoint": null,
  "size": "1024x1024",
  "aspectRatio": "1:1",
  "seed": null,
  "steps": null,
  "sampler": null,
  "cfgScale": null,
  "count": 1,
  "referenceCount": 0
}
```

字段原则：

- 已知就保存真实值。
- 未知就保存 `null` 或不返回，不在 UI 中猜测。
- 参数字段使用稳定 camelCase。
- 原始 provider payload 可以作为 debug 字段后续保存，但不直接展示给普通用户。

详情页展示方式：

```txt
Prompt
Reference Images
Advanced Parameters
  model
  size
  aspectRatio
  seed
  steps
  sampler
  cfgScale
```

“使用同任务参数再生成”应优先读取 `generationParams`，而不是从 UI 字段临时拼装。

## 性能与加载策略

资产管理必须从 v1 开始考虑大量图片场景。AI 图片积累速度很快，几百到几千张图片是常态。

### 图片网格加载

图片网格不能一次性渲染所有资产。

必须采用以下策略之一：

- 分页加载
- 无限滚动分页
- 虚拟滚动

v1 推荐：

```txt
SQLite 分页查询
  -> renderer 追加列表
  -> 网格区域虚拟滚动或分页加载
```

如果短期不接虚拟滚动库，至少要做到分页加载和懒加载图片，避免一次性把全部图片挂到 DOM。

### 缩略图策略

资产网格不应该直接加载本地原图。

建议：

- 为每张图片生成缩略图。
- 网格使用缩略图。
- 预览和详情大图再加载较高分辨率资源。
- 缩略图尺寸控制在 UI 所需范围内，例如 256px 或 512px。
- custom protocol 应区分 thumbnail 和 original。

示例：

```txt
artpilot-image://thumbnail/<imageId>
artpilot-image://original/<imageId>
```

收益：

- 降低内存占用。
- 降低首屏加载时间。
- 减少滚动卡顿。
- 避免大量原图同时解码导致 renderer 崩溃。

### 查询策略

列表查询返回轻量字段：

- imageId
- thumbnailUrl
- createdAt
- width
- height
- fileSize
- favorite
- status

详情查询再返回完整字段：

- prompt snapshot
- generationParams
- references
- task context
- cleanup info

不要在列表接口中返回大段 prompt、完整参考图数据或复杂 JSON，除非搜索命中摘要需要。

## 存储空间感知

AI 图片通常体积较大，资产管理应该让用户知道图片库占用了多少空间。

v1.5 建议增加轻量统计：

```txt
共 120 张图片 · 占用 450 MB
```

展示位置：

- 筛选区顶部
- 图片网格右上角
- 空间设置入口附近

统计字段：

- 图片数量
- 总文件大小
- 本月新增数量
- 本月新增大小

v1 可以先做简单版本：

- 从数据库聚合 `COUNT(*)` 和 `SUM(fileSize)`。
- 只统计 Art Pilot 图片库中的已导入图片。
- 如果文件缺失或统计失败，显示“统计不可用”，不阻塞资产页。

这类统计能提升用户安全感，也能为后续清理功能做铺垫。

## 与最近任务的关系

最近任务和资产管理共享底层数据，但入口和组织方式不同。

```txt
generation_tasks
  -> RecentTaskList 按任务展示

generated_images
  -> AssetManagement 按图片展示
```

最近任务可以链接到资产管理：

- 点击某张图：打开资产详情
- 点击“查看全部”：进入资产管理并筛选该任务

资产管理可以链接回任务上下文：

- 查看所属任务
- 查看同任务其他图片
- 使用同任务参数再生成

## v1 范围

建议 v1 做小而完整：

1. 图片资产网格
2. 图片详情面板
3. 按生成时间倒序
4. prompt 搜索
5. 收藏
6. 在 Finder 中显示
7. 复制 prompt
8. 基于此图继续生成
9. 分页加载或虚拟滚动
10. 缩略图优先加载
11. 高级参数展示

暂不做：

- 标签系统
- 相册系统
- 批量导出
- 重复图片检测
- 云同步
- 复杂筛选器
- 完整存储清理工具

## 页面空状态

没有资产时，不要做营销式空页面。

空状态应该直接给出下一步：

- 提示当前还没有生成图片
- 提供“去创作”入口
- 如果图片库路径异常，显示修复入口

示例：

```txt
暂无图片资产
完成一次生成后，图片会出现在这里。
[去创作]
```

## 设计原则

### 1. 资产管理以结果为中心

主列表展示图片，不展示任务。

### 2. 任务信息是上下文

任务、prompt、参考图、Codex thread 都是理解图片来源的上下文，放在详情中。

### 3. 操作必须闭环

用户看到图片后，应该能立即：

- 找到文件
- 复制内容
- 继续创作
- 整理收藏

### 4. 不暴露完整本地路径

UI 默认展示文件名或路径摘要。完整路径可以通过“在 Finder 中显示”完成，不需要常驻在界面上。

### 5. 不重复最近任务

资产管理不是“最近任务 Plus”。如果某个 UI 看起来像任务流，就应该回到最近任务模块。

## 后续演进

v2 可以考虑：

- 标签
- 相册
- 批量操作
- 图片对比
- 使用次数统计
- 派生关系：哪张图基于哪张参考图生成
- 资产评分
- 删除恢复站
- 导出包

最终目标是让 Art Pilot 的资产管理成为一个轻量但可靠的创作素材库，而不是单纯的历史记录列表。
