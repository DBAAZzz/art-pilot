# 提示词管理 v4 方案 CR 报告

## 整体评价

方案方向正确——把变量填写从弹窗移到创作页，解决了当前流程的割裂感。但有几个落地问题需要补充或修正。

---

## 1. 与现有代码的不一致

### 1.1 `ResolvedPromptTemplate` 和 `PromptImageBinding` 的关系

设计稿定义了新的 `PromptImageBinding` 类型：

```ts
export type PromptImageBinding = {
  variableKey: string
  variableLabel: string
  role?: PromptImageVariable['role']
  imageReferenceIds: string[]
  startIndex: number
  count: number
}
```

但现有的 `ResolvedPromptTemplate`（`packages/shared/src/prompt.ts`）已经有 `imageInputs`：

```ts
imageInputs: Array<{
  variableKey: string
  role?: 'reference' | 'character' | 'style' | 'composition'
  imageIds: string[]
}>
```

`PromptImageBinding` 比 `imageInputs` 多了 `variableLabel`、`startIndex`、`count`，少了直接的 `imageIds`。设计稿没有说明这两个类型之间的转换关系——是 `PromptImageBinding` 替代 `imageInputs`，还是在 `imageInputs` 基础上补充？建议明确，否则实现时会困惑。

### 1.2 `generation_tasks` 表缺少模板相关列

设计稿提到要加三列：

```sql
ALTER TABLE generation_tasks ADD COLUMN prompt_template_id TEXT;
ALTER TABLE generation_tasks ADD COLUMN prompt_template_values_json TEXT;
ALTER TABLE generation_tasks ADD COLUMN prompt_template_image_bindings_json TEXT;
```

但没有提迁移策略。当前的 `schema.sql` 用的是 `CREATE TABLE IF NOT EXISTS`，没有版本管理机制。需要补充：是直接改 schema 文件让新安装生效 + 手写 ALTER 迁移给老用户？还是引入正式的 migration 机制？

### 1.3 缺少按 ID 获取模板的接口

设计稿说创作页收到 `templateId` 后"加载模板"，但当前 `PromptService` 只有 `listPromptTemplates()`（返回全部），没有 `getPromptTemplateById(id)` 方法。

两个选择：

- **新增 `prompt:get-template` IPC 通道 + `getPromptTemplateById` 服务方法**（推荐，干净）
- 前端调 `listPromptTemplates()` 后 filter（简单但浪费）

设计稿应明确用哪种。

## 2. 关键流程遗漏

### 2.1 图片变量的文件路径问题

当前 `UsePromptTemplateDialog`（`apps/desktop/src/features/PromptManagement/index.tsx`）处理图片变量时，会把用户选择的文件转为 `ImageReference`（带 `path`）。设计稿说创作页要承担这个职责，但没有说明图片变量值在前端如何持久化：

- `PromptVariableValue` 的 image 类型只有 `imageIds: string[]`，这是模板定义里的 ID，不是用户选的文件
- 用户选择的文件路径存在哪里？是扩展 `PromptVariableValue` 加 `filePath`，还是用独立的 state 管理？

这直接影响 `imageInputs` 到 `ImageReference[]` 的映射逻辑，需要明确。

### 2.2 "输入图片说明"的注入位置

设计稿说由主进程根据 `imageBindings` 构建图片映射说明，注入到 prompt 中。当前 `CodexImageProvider`（`apps/desktop/electron/providers/codexImageProvider.ts`）的 prompt 构建逻辑是：

```txt
请使用 ImageGen skill 根据以下提示生成图片。
必须生成 ${count} 张图片。
图片尺寸：${size}
参考图数量：${references.length}

${prompt}
```

需要在 `${prompt}` 前插入"输入图片说明"段。设计稿应该明确：这段说明是在 `CodexImageProvider.generateStreaming` 里拼接，还是在 `ImageGenerationService` 层拼接好再传给 provider？建议前者，保持 provider 作为 prompt 构建的单一职责。

### 2.3 模板不存在时的容错

创作页通过 `templateId` 加载模板，如果模板在用户填写变量期间被删除了怎么办？设计稿没有提。至少需要在生成时（调 `resolvePromptTemplate`）处理 "template not found" 错误，给用户友好提示。

## 3. 类型/接口设计问题

### 3.1 `ImageGenerationRequest` 扩展后的语义

设计稿建议：

```ts
export type ImageGenerationRequest = {
  prompt: string
  count?: number
  aspectRatio?: ImageGenerationAspectRatio
  size?: ImageGenerationSize
  references?: ImageReference[]
  promptTemplateUse?: {
    templateId: string
    values: PromptVariableValue[]
    imageBindings: PromptImageBinding[]
  }
}
```

问题是：当有 `promptTemplateUse` 时，`prompt` 和 `references` 的语义变了——`prompt` 应该是模板解析后的 generationPrompt，`references` 应该是图片变量 + 手动参考图合并后的有序列表。但类型上看不出来，容易误用。建议加注释或用 branded type 区分。

### 3.2 `PromptImageBinding.startIndex` 的基数

设计稿说 `startIndex` 是 1-based。但 JavaScript/TypeScript 数组是 0-based。如果 `references` 数组直接用 index 映射，0-based 更自然；如果是为了人可读的"第 N 张"，1-based 更好。需要明确，并在代码里统一，避免 off-by-one bug。

## 4. 建议补充的内容

| 缺失项 | 说明 |
|---------|------|
| `MAX_IMAGE_REFERENCES` 合并限制 | 图片变量 + 手动参考图总数上限是多少？当前 GenerationForm 限制 5，合并后是否沿用？ |
| 创作页 Prompt 区域的组件选型 | 当前 GenerationForm 用的是 plain textarea，模板模式下是否换成 PromptContentEditor？还是保持 textarea 只展示 previewPrompt？ |
| "退出模板模式"的交互细节 | 退出后是否清空变量值？手动参考图是否保留？是否需要确认弹窗？ |
| 模板模式下的 header 变化 | 设计稿提到创作页要显示模板名和"退出模板"按钮，header 的变化由谁控制？当前 AppHeader 是全局的。 |
| 图片变量的缩略图存储 | 用户选了图片后，缩略图用 dataUrl 还是文件路径？大图 dataUrl 会占内存。 |
| `generation_params` 的扩展 | 设计稿提到在 `generation_params` 里加 `promptTemplateId` 和 `promptTemplateTitle`，但 `generation_params` 在当前代码里是什么？是 `references_json` 那一列还是独立字段？需要确认。 |

## 5. 实施步骤的依赖关系

设计稿列了 11 步，但有些步骤之间有隐含依赖：

- 第 3 步（创作页增加模板运行状态）依赖第 2 步（跳转传 templateId），但更依赖"按 ID 获取模板"的接口——这个接口没列在步骤里
- 第 5 步（图片变量选择逻辑迁移）依赖第 1 步（删除弹窗），但如果先删后建，中间状态会 broken——建议先建后删
- 第 6 步（生成前调 resolvePromptTemplate）依赖第 4 步（变量面板），但面板需要能触发 resolve——需要前端的 parser 也支持实时预览

建议调整为：**先加接口和组件，再切换入口，最后清理旧代码**。

### 建议的实施顺序

1. 新增 `getPromptTemplateById` IPC 接口
2. 扩展 `generation_tasks` 表（含迁移策略）
3. 扩展 `ImageGenerationRequest` 类型
4. 创作页增加模板运行状态 + 变量面板组件
5. 图片变量选择逻辑从 PromptManagement 迁移到创作页
6. 生成前调 `resolvePromptTemplate`，构建有序 references 和 imageBindings
7. `CodexImageProvider` 注入"输入图片说明"
8. 创作页 header 增加模板名和退出按钮
9. 资产详情页展示模板来源
10. 切换入口：PromptManagement 的"使用模板"改为跳转创作页
11. 删除 `UsePromptTemplateDialog` 和旧的弹窗流程

---

## 总结

方案核心思路没问题，主要需要补充：

1. **图片变量的文件路径在前端如何管理**（这是最大的设计缺口）
2. 按 ID 获取模板的 IPC 接口
3. 数据库迁移策略
4. `ResolvedPromptTemplate.imageInputs` 和 `PromptImageBinding` 的关系要对齐
5. 实施步骤调整为"先建后拆"的顺序
