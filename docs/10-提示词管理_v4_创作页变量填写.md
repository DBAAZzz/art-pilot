# 提示词管理 v4 方案：创作页变量填写

## 背景

v3 已经把提示词从“静态收藏”升级成“可填写的模板”，支持文本变量和图片变量。当前实现里，用户在提示词管理页点击“使用模板”后，会先弹出变量填写弹窗：

```txt
提示词管理页
  -> 点击使用模板
  -> 弹窗填写变量
  -> 解析最终 prompt
  -> 跳转创作页
  -> 点击生成
```

这个流程可以工作，但用户心智仍然有割裂感：

- 提示词管理页承担了“填写生成参数”的职责。
- 创作页只接收已经解析好的 prompt，无法继续感知模板来源和变量结构。
- 历史任务只能看到最终 prompt，无法知道它来自哪个模板、使用了哪些变量值。
- 图片变量会被提前转换成参考图，创作页无法区分“模板图片变量”和“用户额外参考图”。

v4 的核心调整是：**提示词管理页只负责选择模板，创作页负责填写变量和发起生成**。

## 目标

- 点击“使用模板”后直接进入创作页，不再先弹变量填写弹窗。
- 在创作页 Prompt 输入区下方展示模板变量面板。
- 用户在创作页填写变量后，才能发起生成。
- 生成任务需要保存模板 ID 和变量填写值，方便后续追溯和复用。
- 图片变量和手动参考图在 UI 心智上保持两个体系。
- 生成请求发出时，图片变量和手动参考图可以合并为有序输入图片。
- 多个图片变量必须能稳定映射到对应的 `--image` 顺序。
- 不把本地图片路径或 `file://` URL 直接拼进 prompt 正文。

## 非目标

- 不做复杂变量表达式、条件语法或循环。
- 不做图片变量权重、局部区域绑定或蒙版。
- 不做远程图片资产管理。
- 不在 v4 引入完整模板运行记录详情页。
- 不要求所有历史任务都能回填旧版本没有保存的变量值。

## 核心决策

### 1. 使用模板时直接跳转创作页

提示词管理页点击“使用模板”后，只传模板身份，不解析最终 prompt：

```ts
navigate('/', {
  state: {
    promptTemplateUse: {
      templateId: prompt.id,
    },
  },
})
```

创作页收到 `templateId` 后加载模板，并在 Prompt 输入区域下方显示变量填写面板。

模板加载不建议通过 `listPromptTemplates()` 后前端 filter。v4 应新增按 ID 获取模板的 IPC：

```txt
IPC_CHANNELS.prompt.getTemplate
  -> window.api.getPromptTemplateById(templateId)
  -> PromptController
  -> PromptService.getPromptTemplateById(templateId)
```

如果模板不存在，主进程返回 `null` 或抛出明确错误。创作页需要显示友好提示：

```txt
模板不存在或已被删除，请返回提示词管理页重新选择。
```

生成前调用 `resolvePromptTemplate` 时，也必须继续处理模板不存在的错误，因为用户可能在填写期间删除了模板。

### 2. 创作页成为模板运行时

创作页需要同时维护三类状态：

```txt
普通创作状态
  - prompt
  - aspectRatio
  - imageCount
  - manualReferences

模板运行状态
  - templateId
  - template
  - variableValues
  - imageVariableImages

解析结果
  - previewPrompt
  - generationPrompt
  - imageVariableMappings
  - validationErrors
```

当存在模板运行状态时：

- Prompt 主输入框可以显示最终 prompt 预览，或显示模板正文预览。
- 变量面板显示在 Prompt 输入区下方。
- 生成按钮根据变量校验结果决定是否可用。
- 用户可以退出模板模式，回到普通 prompt 创作。

### 3. 生成时再解析模板

用户点击生成时才调用：

```ts
window.api.resolvePromptTemplate({
  templateId,
  values,
})
```

得到：

```ts
{
  prompt: string
  previewPrompt: string
  imageInputs: Array<{
    variableKey: string
    role?: 'reference' | 'character' | 'style' | 'composition'
    imageIds: string[]
  }>
}
```

随后 renderer 将 `imageInputs` 映射为本地 `ImageReference[]`，并与用户手动添加的参考图合并，再调用 `startImageGeneration`。

这里需要明确：`ResolvedPromptTemplate.imageInputs` 不被 `PromptImageBinding` 替代。二者职责不同：

```txt
ResolvedPromptTemplate.imageInputs
  - 来自模板解析结果
  - 只描述变量 key、role 和用户填写的 imageIds
  - 不关心最终 references 数组里的位置

PromptImageBinding
  - 来自生成前的 references 编排结果
  - 负责把变量图片映射到最终输入图片序号
  - 用于 Codex prompt 中生成“第 N 张输入图”说明
  - 用于 generation task 历史记录
```

转换关系：

```txt
imageInputs
  + imageVariableImages
  + template.variables
  + manualReferences
  -> orderedReferences
  -> imageBindings
```

## 图片变量与参考图的关系

图片变量和参考图应保持两个体系：

```txt
图片变量
  - 来自模板定义
  - 有 key、label、role、required、maxCount
  - 用户为某个变量填写图片
  - 用于表达结构化语义：角色图、风格图、构图图等

手动参考图
  - 来自创作页全局参考图入口
  - 没有变量 key
  - 用于表达本次生成的额外参考
```

但在调用 Codex CLI 时，它们最终都会变成输入图片附件：

```txt
template image variables
  + manual references
  -> ordered ImageReference[]
  -> codex exec --image <path1> --image <path2> ...
```

这里的关键是：**合并不等于丢失语义**。图片变量的 key、label、role 和顺序必须写入生成 prompt 的图片说明段。

## 图片变量文件路径如何管理

`PromptVariableValue` 不应该直接扩展成保存文件路径。它仍然只保存模板变量值：

```ts
export type PromptVariableValue =
  | {
      key: string
      type: 'text'
      value: string
    }
  | {
      key: string
      type: 'image'
      imageIds: string[]
    }
```

用户选择的图片文件由创作页维护独立 state：

```ts
export type PromptImageInputValue = {
  id: string
  name: string
  path: string
  imageUrl: string
  mimeType?: string
}

type ImageVariableImagesByKey = Record<string, PromptImageInputValue[]>
```

其中：

- `id` 是 renderer 生成的临时 ID，用于和 `PromptVariableValue.imageIds` 对齐。
- `path` 来自 `window.api.getPathForFile(file)`，是主进程最终传给 Codex 的真实本地路径。
- `imageUrl` 用于 renderer 缩略图预览，可以是 `dataUrl` 或受控协议 URL。
- `PromptVariableValue.imageIds` 只引用这些临时 ID，不直接携带路径。

这样可以保持三层职责清晰：

```txt
PromptVariableValue
  -> 模板解析和必填校验

ImageVariableImagesByKey
  -> renderer 文件选择、缩略图和路径映射

ImageReference
  -> 生成请求给主进程的图片输入
```

v4 第一版可以继续使用当前弹窗里已有的 `createPromptImageInputValue(file)` 思路，将它迁移到创作页变量面板。后续如果引入资产系统，再把临时 ID 替换成正式 asset ID。

## 多图片变量如何稳定对应 `--image`

如果一个模板有 3 个图片变量：

```txt
{{character_image}}
{{style_image}}
{{background_image}}
```

单纯传：

```bash
codex exec --image /path/character.png --image /path/style.png --image /path/background.png -- -
```

只能保证输入图片的顺序，不能天然保证模型知道“第几张对应哪个变量”。因此需要同时做两件事：

1. 生成有序附件列表。
2. 在 prompt 中写入图片变量映射说明。

推荐顺序规则：

```txt
1. 按模板 variables 数组顺序遍历图片变量。
2. 每个图片变量内部按用户选择顺序展开。
3. 得到 templateImageReferences。
4. 再追加 manualReferences。
5. 按最终数组顺序传给 Codex CLI。
```

同时在最终 prompt 前追加一段系统化说明：

```txt
输入图片说明：
- 第 1 张输入图：变量 character_image（角色参考），用于保持主角身份、发型、服装和脸部特征。
- 第 2 张输入图：变量 style_image（风格参考），用于参考整体视觉风格。
- 第 3 张输入图：变量 background_image（构图参考），用于参考背景和构图。
- 第 4 张输入图：额外参考图 1，由用户在创作页手动添加。

请严格按上述映射理解输入图片，不要混淆变量用途。
```

再拼接解析后的用户 prompt：

```txt
用户提示：
<generationPrompt>
```

这样即使 Codex/ImageGen 只接收一组 `--image`，模型仍然能通过文本说明建立“第 N 张图 -> 变量 key / role”的映射。

## 不建议把图片变量替换成 URL

不要把图片变量替换成：

```txt
{{character_image}} -> file:///Users/xxx/a.png
```

也不要替换成：

```txt
{{character_image}} -> /Users/xxx/a.png
```

原因：

- 模型不会因为 prompt 文本里出现本地路径就读取图片。
- `file://` URL 是 renderer 展示概念，不是模型输入。
- 本地路径直接进入 prompt 会暴露实现细节，也可能影响生成质量。
- 真正的图片输入应通过 Codex CLI 的 `--image <localPath>` 传递。

推荐做法：

```txt
图片变量占位符
  -> generation prompt 中替换为空
  -> imageInputs 结构化返回
  -> renderer 映射为 ImageReference
  -> main process 通过 --image path 传给 Codex
  -> prompt 中追加“输入图片说明”
```

## 数据结构调整

### ImageGenerationRequest

建议扩展生成请求：

```ts
export type ImageGenerationRequest = {
  prompt: string
  count?: number
  aspectRatio?: ImageGenerationAspectRatio
  size?: ImageGenerationSize
  references?: ImageReference[]
  promptTemplateUse?: {
    templateId: string
    values: PromptVariableValue[]
    imageBindings: PromptImageBinding[]
  }
}

export type PromptImageBinding = {
  variableKey: string
  variableLabel: string
  role?: PromptImageVariable['role']
  imageReferenceIds: string[]
  startIndex: number
  count: number
}
```

其中 `startIndex` 明确使用 **1-based 序号**，对应最终给用户和模型说明的“第 N 张输入图”。代码读取 `references` 数组时必须转换：

```ts
const reference = references[startIndex - 1]
```

选择 1-based 的原因是 prompt 中要写给模型和用户阅读，`第 1 张输入图` 比 `index 0` 更自然。所有数组访问必须集中在 helper 中完成，避免 off-by-one bug。

`prompt` 和 `references` 在模板模式下也要写清语义：

```ts
export type ImageGenerationRequest = {
  // 普通模式：用户输入的 prompt。
  // 模板模式：模板解析后的 generationPrompt，不包含图片变量占位符。
  prompt: string

  // 普通模式：用户手动添加的参考图。
  // 模板模式：图片变量参考图 + 用户手动参考图合并后的最终有序列表。
  references?: ImageReference[]

  promptTemplateUse?: {
    templateId: string
    values: PromptVariableValue[]
    imageBindings: PromptImageBinding[]
  }
}
```

### generation_tasks

开发阶段可以直接改 `schema.sql`，不需要设计正式迁移。建议新增列：

```sql
prompt_template_id TEXT,
prompt_template_values_json TEXT,
prompt_template_image_bindings_json TEXT
```

也可以先只放进 `generation_params`，但不推荐长期这样做。独立列更方便：

- 资产详情展示“来自模板”。
- 后续按模板筛选资产。
- 从历史任务重新带入模板变量再生成。
- 统计模板使用效果。

### generation_params

`generation_params` 仍然保留一份冗余摘要：

```json
{
  "count": 1,
  "size": "1024x1024",
  "aspectRatio": "1:1",
  "referenceCount": 4,
  "promptTemplateId": "template-id",
  "promptTemplateTitle": "模板标题"
}
```

## 创作页 UI

当创作页处于模板模式时，红框区域显示变量面板：

```txt
模板：产品海报生成
[退出模板]

文本变量
  标题 / 主体 / 风格 ...

图片变量
  角色参考图
  风格参考图
  构图参考图

最终 Prompt 预览
  ...
```

变量面板建议规则：

- 必填变量为空时显示错误提示。
- 图片变量达到 `maxCount` 后禁用继续添加。
- 图片变量缩略图只表示变量输入，不自动放到全局参考图区。
- 手动参考图仍然显示在 Prompt 输入框里的参考图区。
- 生成按钮旁可以显示“模板变量 3/5 已填写”。

Prompt 主输入框组件第一版建议保持现有 `GenerationForm` 的 textarea，不强行切换为 `PromptContentEditor`：

- 普通模式：textarea 仍然是用户可编辑 prompt。
- 模板模式：textarea 可以显示 `previewPrompt` 或 `generationPrompt`，但默认不建议用户直接编辑模板解析结果。
- 如需允许用户追加描述，建议新增“补充描述”输入，而不是修改模板正文。

退出模板模式：

- 清空 `templateId`、模板对象、变量值和图片变量图片。
- 保留用户手动添加的参考图。
- 如果变量已填写或图片变量已选择，点击退出时建议二次确认。
- 退出后 prompt 输入框回到普通模式；是否保留当前 `generationPrompt` 可作为确认弹窗选项，第一版可直接清空。

模板模式下的 header 不必改全局 AppHeader。建议在变量面板顶部显示模板名和“退出模板”按钮，避免把局部编辑状态塞进全局标题栏。

## 生成流程

```txt
用户在 PromptManagement 点击使用模板
  -> navigate('/', { promptTemplateUse: { templateId } })

ImageGenerationPage
  -> 通过 getPromptTemplateById 加载模板详情
  -> 初始化变量默认值
  -> 展示变量面板

用户填写变量
  -> renderer 用 shared parser 做实时预览和校验

用户点击生成
  -> main process resolvePromptTemplate(templateId, values)
  -> renderer 将 imageInputs 映射到 ImageReference
  -> 构建有序 references
  -> 构建 imageBindings
  -> startImageGeneration({
       prompt: promptWithImageMapping,
       references,
       promptTemplateUse
     })

main process
  -> 保存 generation_tasks，包含 templateId 和 values
  -> CodexImageProvider 使用 references.map(path) 传 --image
  -> Codex prompt 中包含图片映射说明
```

## prompt 拼接建议

最终传给 Codex 的 prompt 不应只包含用户 prompt，而应由 provider 统一包装：

```txt
请使用 ImageGen skill 根据以下提示生成图片。
必须生成 1 张图片。
图片尺寸：1024x1024
参考图数量：4

输入图片说明：
- 第 1 张输入图：变量 character_image（角色参考），用于保持主角身份、发型、服装和脸部特征。
- 第 2 张输入图：变量 style_image（风格参考），用于参考整体视觉风格。
- 第 3 张输入图：变量 background_image（构图参考），用于参考背景和构图。
- 第 4 张输入图：额外参考图 1。

请严格按上述映射理解输入图片。

用户提示：
<resolved generation prompt>
```

这里的“输入图片说明”应由主进程根据 `promptTemplateUse.imageBindings` 和最终 `references` 构建，避免 renderer 和 main process 的序号规则不一致。

具体注入位置建议放在 `CodexImageProvider.buildImageGenerationPrompt` 内。原因是 provider 当前已经负责包装 Codex prompt：

```txt
生成数量
图片尺寸
参考图数量
用户提示
```

继续由 provider 插入“输入图片说明”，可以保持 prompt 构建职责集中。`ImageGenerationService` 只负责校验、保存任务和传递结构化请求，不拼接模型提示词。

## 兼容策略

普通 prompt 创作不受影响：

```txt
promptTemplateUse: undefined
```

旧的从提示词管理页弹窗解析流程可以删除，或短期保留为内部组件，但不再作为主路径。

历史任务如果没有 `prompt_template_id`，资产详情页只展示普通 prompt。

## 实施步骤

推荐采用“先建后拆”的顺序，避免中间状态 broken：

1. 新增 `getPromptTemplateById` IPC 接口。
2. 扩展 shared 类型：`ImageGenerationRequest.promptTemplateUse` 和 `PromptImageBinding`。
3. 开发阶段直接更新 `schema.sql`，给 `generation_tasks` 增加模板相关列。
4. ImageGenerationPage 增加模板运行状态。
5. 创作页新增 `PromptTemplateVariablePanel`。
6. 将图片变量选择逻辑复制或迁移到创作页变量面板。
7. 生成前调用 `resolvePromptTemplate`，处理模板不存在错误。
8. 构建有序 references 和 imageBindings，并校验总数不超过 `MAX_IMAGE_REFERENCES`。
9. CodexImageProvider 在 prompt 中注入“输入图片说明”。
10. ImageHistoryService 保存模板 ID、变量值和图片映射。
11. 资产详情页展示模板来源和变量摘要。
12. 切换入口：PromptManagement 的“使用模板”改为直接跳转创作页。
13. 删除 `UsePromptTemplateDialog` 和旧弹窗流程。

## 风险与注意事项

- 图片变量和手动参考图合并后总数仍受 `MAX_IMAGE_REFERENCES` 限制。
- 图片变量映射必须使用最终 references 数组的顺序，不能用变量局部顺序。
- renderer 中的 `imageUrl` 只能用于预览，不能作为模型输入。
- `ImageReference.path` 是主进程传给 Codex 的真实本地路径。
- 模板不存在、模板变量变更、图片路径失效都要在生成前给出明确错误。
- 如果未来接入非 Codex 模型，`imageBindings` 仍然有价值，可由模型适配层转换成不同 provider 的图片输入格式。

## 结论

v4 应把模板变量填写移动到创作页。提示词管理页负责“选择模板”，创作页负责“填写变量、组织参考图、发起生成”。

图片变量不应被替换成 URL，而应转换为结构化图片输入。多个图片变量通过“有序 `--image` 附件 + prompt 中的输入图片说明 + generation task 中的 imageBindings”三者共同保证映射关系稳定。
